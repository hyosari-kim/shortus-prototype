# Part1 가설 1 구현 계획: 편집·디자인 단계 통합

> 이후 범위 조정: 검증 지표 계측, 지표 패널, 기존 흐름과의 전환은 모두 뺐다. 기존 흐름은 실서비스에서 보고, 프로토타입에는 가설을 적용한 흐름만 둔다.

## 목표

편집과 디자인을 하나의 화면으로 합쳐, 편집을 시작한 뒤 영상 제작을 요청할 때까지 걸리는 시간과 그 사이의 전환율을 기존 흐름과 비교할 수 있게 만든다.

가장 작은 형태: 기존 흐름(baseline)은 그대로 두고, 통합 흐름(merged)을 하나 더 만든다. 두 흐름을 사이드바에서 바꿔 가며 같은 지표로 잰다.

## 범위

**한다**
- 통합 화면 하나: 같은 미리보기 위에서 구간·자막·디자인을 고친다
- 흐름 전환 토글 (기존 / Part1 개선)
- 검증 지표 수집과 표시: 편집 시작 → 제작 요청 소요 시간, 전환율

**하지 않는다**
- 실제 사용자 A/B 배정, 서버 저장, 통계적 유의성 판단
- 장면·댓글 탭, 고급 에디터 (기존 목업 그대로)
- 디자인 세부 선택 화면 (줄을 누르면 다음 값으로 넘어가는 방식 유지)

## 데이터 형태 (완료)

`src/model.ts`에 이미 반영했다. 빌드 확인은 아직 하지 않았다.

```ts
type Variant = 'baseline' | 'merged'

Project += {
  variant: Variant              // 시작할 때 고정. 진행 중에 토글해도 지표가 섞이지 않는다
  editStartedAt: number | null  // 처음 편집 단계에 들어온 시각
  makeRequestedAt: number | null
}

type Metric = { started: number; made: number; totalMs: number }
State += {
  variant: Variant                    // 다음에 시작할 숏폼에 쓸 흐름
  metrics: Record<Variant, Metric>
}
```

상태 전이 규칙:
- `goto edit`를 처음 받으면 `editStartedAt`을 남기고 그 흐름의 `started`를 1 올린다.
- `make`를 처음 받으면 `made`를 1 올리고 `totalMs`에 (요청 시각 − 편집 시작 시각)을 더한다. 결과 화면에서 다시 고쳐 만들면 두 번 세지 않는다.
- merged 흐름에서 `goto design`은 `edit`로 바꾼다. 통합 흐름에는 디자인 단계가 없다.
- 지표 정의: 전환율 = made / started, 평균 소요 = totalMs / made.
- 자동 완성으로 편집을 건너뛴 숏폼은 지표에 넣지 않는다. 편집을 시작하지 않았기 때문이다.
- 저장 키를 `v2`로 올렸다. 예전 저장 데이터에는 새 필드가 없어서다.

## 화면 구조

다루는 객체:
- **후보(숏폼)**: 구간, 제목, 첫 자막, 개별 디자인(있으면)
- **디자인 설정**: 템플릿, 폰트, 화면 비율, 자동 컷, 세부 설정. 공용 값과 후보별 값 두 층이다.

후보 하나를 고르면 그 후보에 대한 모든 수정(구간, 자막, 디자인)이 같은 미리보기에 바로 반영된다. 이것이 통합 화면의 중심이다.

### 레이아웃: 기존 편집 화면 + 디자인 탭 (사용자 선택, B안)

지금 편집 화면을 그대로 쓰고 두 군데만 바꾼다.

- 왼쪽 패널 탭: 구간 · 자막 · **디자인** · 장면 · 댓글. 디자인 탭에는 기존 디자인 화면의 "이 후보에만 / 후보 N개 모두에" 범위 전환과 설정 줄(템플릿, 폰트, 화면 비율, 자동 컷, 세부 설정)을 그대로 옮긴다.
- 하단 오른쪽 버튼: "디자인으로 이동" 대신 "영상 만들기 (N개)".
- 오른쪽 미리보기는 그대로 두되, 디자인(화면 비율, 템플릿, 폰트)도 반영한다. 기존 흐름의 미리보기에도 같은 조각을 쓴다.
- 상단 후보 탭, 막힌 후보 알림은 기존과 같다.
- 스텝퍼: 입력 · 후보 · 편집·디자인 · 만들기 · 결과 (5단계)

선택 이유: 바뀌는 것이 "단계 하나를 없앴다"뿐이라, 두 흐름의 지표 차이를 단계 통합의 효과로 읽기 쉽다. 대가는 디자인 설정이 탭 뒤에 있다는 점이다.

## 구현 순서

각 단계는 확인으로 끝난다.

1. **빌드 복구.** 모델 변경에 맞춰 화면 코드 타입 오류를 고친다.
   → 확인: `npm run build` 통과
2. **공용 조각 분리.** 디자인 설정 목록(`DesignSettings`)과 디자인을 반영하는 미리보기(`Preview`)를 꺼낸다. 기존 화면은 이 조각을 쓰도록 바꾸기만 한다.
   → 확인: 기존 흐름을 끝까지 눌러 보고 동작이 바뀌지 않았는지 본다
3. **통합 화면.** 편집 화면이 `project.variant`가 merged이면 디자인 탭과 "영상 만들기" 버튼을 보인다. 스텝퍼는 흐름에 따라 5단계 또는 6단계로 보인다.
   → 확인: 통합 흐름에서 후보 → 편집 → 만들기 → 결과로 디자인 단계 없이 간다. 구간·자막·디자인을 바꾸면 미리보기에 바로 반영된다
4. **흐름 토글과 지표 패널.** 사이드바에 "기존 / Part1 개선" 전환과 흐름별 지표(편집 시작 수, 제작 요청 수, 전환율, 평균 소요)를 둔다. 진행 중인 숏폼이 있으면 "다음 숏폼부터 적용"이라고 적는다.
   → 확인: 두 흐름을 한 번씩 끝까지 돌리고 지표 숫자가 각 흐름에 따로 쌓이는지 저장 상태로 대조한다. 결과에서 다시 만들어도 두 번 세지 않는지 본다
5. **브라우저 검증.** 두 흐름을 같은 시나리오(유튜브 예시, 직접 편집, 후보 2개 선택, 템플릿 1회 변경)로 돌리고 화면 이동 횟수와 지표를 기록한다.
   → 확인: 스크린샷과 지표 값을 README에 붙인다
6. **문서.** README에 Part1 가설 1이 어디까지 됐는지, 무엇을 측정하는지, 무엇이 남았는지 적는다.

## 위험과 대응

- **디자인이 탭 뒤에 숨는다.** 디자인을 바꾸는 사람이 탭을 못 찾으면 통합 효과가 줄어든다. 디자인을 바꾼 비율을 따로 보면 판단에 도움이 되지만, 이번 범위에서는 재지 않는다.
- **화면 복잡도.** 탭 하나만 늘어서 복잡도 증가는 작다. 프로토타입에서는 정성적으로만 확인한다.
- **프로토타입 지표의 한계.** 한 브라우저에서 사람이 직접 누른 기록이라 실제 전환율이 아니다. 계측 지점이 맞는지와 흐름 비교 구조를 보여 주는 데 의미가 있다.
