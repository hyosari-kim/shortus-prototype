# ShortUs 숏폼 생성 퍼널 프로토타입

실서비스의 숏폼 제작 흐름을 화면 캡처를 보고 재현하고, 그 위에 우선순위 가설을 적용한 프로토타입입니다. 실서비스 코드에는 접근하지 않았습니다. 가설을 적용하기 전의 흐름은 실서비스에서 보면 되므로, 이 프로토타입에는 가설을 적용한 흐름만 둡니다.

흐름: 내 숏폼 → 입력 → 후보 → 편집·디자인 → 만들기 → 결과

## 실행

```bash
npm install
npm run dev
```

사이드바의 "데모 초기화"를 누르면 크레딧과 진행 중인 숏폼이 처음 상태로 돌아갑니다.

## 데모 시나리오

| 입력 | 방식 | 흐름 |
| --- | --- | --- |
| 예시 "유튜브(스포츠)" | 직접 편집 또는 자동 완성 | 분석 → 후보 4개(자동 생성이 막힌 후보 3개) → 편집·디자인 → 만들기 → 결과 |
| 예시 "기사" | 자동 완성 | 분석 → 막힌 후보가 없어 후보·편집·디자인을 건너뛰고 바로 만들기 → 결과 |

## 구조

모든 화면은 `Project` 객체 하나를 읽고, 바꿀 때는 액션만 보냅니다. 가설 하나를 얹을 때 손대는 곳이 그 단계 화면과 리듀서의 해당 분기로 좁혀지게 하려는 구조입니다.

- `src/model.ts`: 타입, 고정 데이터(AI 분석 결과 대신 쓰는 값), 리듀서. 퍼널 규칙은 전부 여기에 있습니다.
  - 분석 비용은 1분에 4크레딧이고, 분석이 끝나 후보가 나올 때 차감합니다.
  - 자동 완성 모드에서 막힌 후보가 없으면 `candidates`를 건너뛰고 `rendering`으로 갑니다.
  - 디자인은 공용(`sharedDesign`)과 후보별(`candidate.design`) 두 단계입니다. "후보 N개 모두에"로 바꾸면 후보별 값을 지웁니다.
  - 막힌 후보로 만들기를 누르면 `rightsConfirmedAt`에 권리 확인 시각을 남깁니다.
- `src/store.tsx`: `useReducer`와 `localStorage` 저장. 새로고침해도 단계가 유지됩니다.
- `src/screens/*`: 단계별 화면. 분석과 렌더는 `Progress` 하나가 맡고, 진행률은 저장하지 않고 단계 시작 시각에서 계산합니다.
- `src/ui.tsx`: 사이드바, 스텝퍼, 썸네일, 모달, 막힌 후보 알림 같은 공용 조각.

## Part1 가설 1. 편집·디자인 단계 통합

계획: [docs/hypothesis-1-plan.md](docs/hypothesis-1-plan.md)

### 어디까지 만들었나

| 항목 | 상태 |
|---|---|
| 통합 화면 (편집 화면에 디자인 탭 추가, 하단 버튼을 "영상 만들기"로) | 완료 |
| 디자인 변경을 같은 미리보기에 반영 (템플릿, 폰트, 화면 비율) | 완료 |
| 실제 사용자 A/B 배정, 서버 저장, 유의성 판단 | 하지 않음 (프로토타입 범위 밖) |

레이아웃은 세 안(미리보기 + 인스펙터, 기존 편집 화면 + 디자인 탭, 3단 에디터) 중 두 번째를 골랐습니다. 바뀌는 것이 "단계 하나를 없앴다"뿐이라, 실서비스와의 차이가 단계 통합으로 바로 보입니다. 대가는 디자인 설정이 탭 뒤에 있다는 점입니다.

### 실서비스와 비교

같은 시나리오(유튜브 예시, 직접 편집, 후보 2개 선택, 템플릿 1회 변경)에서 편집 시작부터 제작 요청까지를 비교했습니다. 실서비스 쪽은 재현 화면 기준입니다.

| | 실서비스 | 이 프로토타입 |
|---|---|---|
| 편집 시작 → 제작 요청 사이 화면 이동 | 1번 (편집 → 디자인) | 0번 |
| 같은 구간의 클릭 수 | 4번 (디자인으로 이동, 편집 펼치기, 템플릿, 영상 만들기) | 3번 (디자인 탭, 템플릿, 영상 만들기) |

### 남은 것

- 디자인 설정이 탭 뒤에 있어서, 사용자가 디자인 탭을 찾는지가 이 레이아웃의 가장 큰 위험입니다.

## Part1 가설 2. 쇼츠 후보 선택 화면 개선

후보 단계를 카드 4개 대신 3단 화면으로 바꿨습니다.

| 항목 | 상태 |
|---|---|
| 왼쪽: 후보 목록 (원본 시간순 기본, AI 추천순 전환, 체크로 고르기, 막힌 이유 표시) | 완료 |
| 가운데: 고른 후보의 영상 미리보기만 크게 | 완료 |
| 오른쪽: 후보 번호·제목·길이·원본 구간, AI 선정 점수와 이유, 막힌 이유 안내, 고르기/빼기 | 완료 |
| 실제 영상 재생 | 하지 않음 (고정 데이터) |

- 세 열은 카드 없이 세로 구분선으로만 나눴습니다.
- 선정 이유는 기존 카드의 "선정 이유" 데이터를 그대로 씁니다.
- 정렬은 고려 사항에 맞춰 시간순과 AI 추천순을 모두 두고 시간순을 기본으로 했습니다.

## Part2 가설 1. 내 숏폼에서 개별 영상 확인 및 발행

| 항목 | 상태 |
|---|---|
| 내 숏폼 목록 화면 (필터, 검색, 오른쪽 숏폼 상세) | 완료 |
| 행마다 "영상 n · 발행 m" 표시 (미발행이 남으면 발행 수를 주황색으로) | 완료 |
| "영상 보기"로 펼치는 아코디언, 펼칠 때 그 숏폼의 영상만 불러오는 로딩 | 완료 (0.6초 타이머로 흉내) |
| 영상별 미리보기(모달)와 발행, "남은 n개 모두 발행" | 완료 |
| 발행 채널 선택, 예약 발행, 발행 실패 처리 | 하지 않음 (채널은 "내 채널" 하나로 고정) |

- 지난 숏폼 4개는 고정 데이터입니다. 진행 중인 숏폼은 결과 단계까지 가면 만든 영상이 목록에 나오고, 같은 방식으로 발행할 수 있습니다.
- 발행 상태는 브라우저에 저장되어 새로고침해도 남습니다.

## 목업으로 남긴 것

- 실제 영상, 분석, 렌더링은 없습니다. 썸네일은 그라데이션 블록이고, 분석과 렌더는 각각 6초, 5초 타이머입니다.
- 편집의 장면·댓글 탭, 결과 화면의 다운로드·발행 버튼은 자리만 있습니다.
- 디자인 설정은 줄을 누를 때마다 다음 값으로 넘어갑니다. 세부 선택 화면은 없습니다.

## AI 도구 활용

Claude Code(Opus)로 작업했습니다.

1. 화면 캡처를 넣고 단계별 상태와 규칙(크레딧 차감 시점, 막힌 후보, 자동 완성 분기)을 먼저 타입과 리듀서로 정리하게 했습니다.
2. 그 모델 위에 화면을 생성했습니다.
3. 브라우저 자동화로 직접 편집 경로와 자동 완성 경로를 끝까지 눌러 보며 검증했습니다. 이 과정에서 기사 링크가 크레딧 확인을 건너뛰던 버그를 찾아 고쳤습니다.
4. Part1 가설 1은 구현 전에 계획서를 먼저 쓰게 하고, 레이아웃 세 안의 장단점을 비교한 뒤 사람이 고른 안으로 구현했습니다.
5. 가설마다 사람이 화면을 보고 뺄 것과 옮길 것을 짚으면, 그 지시대로 고치고 브라우저에서 다시 확인하는 식으로 다듬었습니다.
